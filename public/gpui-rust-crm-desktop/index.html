想用 GPUI 做多端 CRM，我先把能跑的和不能吹的分开了

近期有人问我：供应链这边要不要用 GPUI + Rust 做一套多端 CRM 桌面？客户名单、商机看板、跟进表单，还要在 macOS、Windows、Linux 上同一套代码。我第一反应不是画原型，是先把「能跑的」和「不能吹的」分开。

我自己是供应链里做架构的，平时爱折腾 AI 跟桌面工具。CRM 这种活，像配货台：表要沉得住货，表单要过得了闸，面板要能拆能合。框架再炫，扛不住列表和表单，就别急着喊「多端成品」。

· · ·
GitHub 上没有现成的 GPUI CRM

我按 GPUI、Rust、CRM、contacts、pipeline 这些词翻开源仓库。结论很干脆：没有一款能诚实点名、装上就能当 CRM 用的 GPUI 桌面成品。名字像 CRM 的，多数是 Tauri + Web，或者 Dioxus；跟 GPUI 不是一路。

所以这篇不评测「某某 GPUI CRM 品牌」。我评的是零件厂：Zed 同款引擎 GPUI，加上长桥开源的 gpui-kit 组件库。写作这天 GitHub 上，Zed 大约 9.2 万 ★，gpui-kit 大约 1.7 万 ★；crates.io 上 gpui-kit 是 0.7.3，gpui 本体还是 0.2.x 这一档。

· · ·
CRM 要的三块砖：表、表单、可拆面板

桌面 CRM 不是再套一层浏览器。日常密度大概三块：百万级客户/线索要能刷；线索详情要表单齐全；旁边还得能停靠跟进记录、活动流、附件——像仓库里主通道加侧闸口。

官方站点写得很直：gpui-kit 有 75+ 组件与原语，虚拟表声称能扛「数十万行」量级的滚动、固定列、排序与单元格选择；还有 Dock 布局、图表、编辑器、AccessKit（无障碍支持）、可选 WASM（WebAssembly）与 JS 扩展宿主。生产引用是 Longbridge Pro 交易桌面，不是 CRM——但零件清单，刚好对上 CRM 的施工图。

· · ·
我在 Linux 上把 Story 和表格 demo 跑起来了

本机环境：Linux 图形会话，Rust 1.99，release 编译。GPU 路径是 Vulkan 上的 llvmpipe（软件渲染），所以下面只报冷启动与常驻内存，不报「120 帧」这类官方宣传帧率，也不拿软件渲染冒充独显成绩。

先跑官方 hello_world：窗口里一行 Hello，一颗主按钮。从进程起来到 X 窗口可搜到，大约 0.52 秒；窗口起来后 VmRSS 大约 169 MB。二进制体积大约 36 MB。这只证明「能亮」，不证明 CRM 能扛。

本机实测：gpui-kit hello_world，release，冷启动约 0.52 秒，RSS 约 169 MB

再跑 table_in_scrollable：页面里嵌一张 DataTable（数据表），列是 ID / Name / Email / Role / Status——长得像客户列表，但官方 demo 只有几十行样本，不是某款 CRM 产品。冷启动大约 0.27 秒，RSS 大约 148–153 MB。

本机实测：嵌套滚动里的 DataTable，CRM 气质的列，但是示例数据

· · ·
Story 里那张五千行表，才是我要盯的

组件库自带 Story 画廊（CLI 可直接打开指定故事）。我打开 DataTable：界面写着 Rows: 5000，页脚是 Total: 5000 rows · 45 columns；侧栏脚注写着 79 components，版本条是 v0.7.3 / Default Light。冷启动大约 0.27 秒，RSS 大约 225–228 MB；Story 二进制大约 119 MB（本机构建关掉了依赖 ALSA 的 speech 特性）。

本机实测：gpui-component-story DataTable，5000 行 × 45 列控件态，RSS 约 225 MB

同一套 Story 里，Form 有姓名、邮箱、多行简介、生日、开关、色板；Dock 能把 Explorer / Editor / Terminal 拖成可拆分工作区。这两块对 CRM 很实在：线索建档靠表单，多面板跟进靠 Dock。Form / Dock 起来后 RSS 大约落在 195–202 MB 一带。

本机实测：Form 故事——姓名、邮箱、简介、日期与开关，CRM 建档常见件

本机实测：Dock 故事——可拖拽拆分的工作区，适合跟进记录侧栏

· · ·
功能密度够不够，得看零件，不看 PPT

对照一张朴素 CRM 清单：客户/线索列表、详情表单、活动时间线、权限与同步、离线缓存。gpui-kit 公开能力覆盖了列表虚拟化、表单控件、Dock、主题、无障碍与测试钩子；权限模型、多租户同步、移动端，不在这套桌面零件的默认卖点里——Mobile 官方材料也不当成熟交付硬吹；WASM 有，但别当成「浏览器里开完整 CRM」的承诺。

效率上，Rust 原生 UI 省掉一层 WebView 往返，像少了一道中转仓。代价是工程门槛：要跟 rustup、系统依赖、pre-1.0 API 抖动打交道。gpui 还在 0.2.x，生产项目常盯 Zed / 长桥的 pin 版本，文档会变——这点得直说。

· · ·
性能我只认本机测到的，不替官方背书

本机三组 release 粗测（软件渲染，数字有抖动，只当量级）：极简窗 ~0.5 s / ~170 MB；小表格 demo ~0.3 s / ~150 MB；Story 五千行表 ~0.3 s / ~225 MB。官方写「高刷新 / GPU」，我这边没有独显帧率数据，就不多写一句。

虚拟表能不能真吃「数十万行」，官方文档有设计与 API；我本机只亲眼开到 Story 的 5000 行控件态，没有在这篇里伪造更大吞吐。供应链人看性能，宁可少报，也不拿 PPT 当过闸单。

· · ·
想开工的话，我建议这么排期

第一周：clone gpui-kit，先跑 Story 和 hello/table，确认本机依赖齐。第二周：用 DataTable + Form 搭「客户列表 + 详情」薄壳，别急着权限中台。第三周：Dock 把跟进面板嵌进去，再谈同步协议。有现成 SaaS CRM 只是要「更快桌面壳」的，先问自己是不是更适合 Tauri；真要信息密度和原生手感，GPUI 这条零件链，目前是少数能把表和面板都做沉的选择。

回到开头那句：多端 CRM 可以做，但先承认——成品 CRM 还得自己焊，能跑的是零件厂，不能吹的是「已经有一款 GPUI CRM 等你装」。零件够沉，施工图也清楚；剩下的，是业务边界，不是又一篇框架安利。
