【公众号账号】

报价单发来的是 PDF，物料和金额都看得见。可要把它并进采购明细，鼠标一拖，复制出来的字却不再按列排。重新抄一遍，最不放心的还不是物料名称，而是编码开头的零和金额的小数位。

表格有边框，字也清楚，看起来只差一个“提取”按钮。我也容易顺着这个直觉，觉得让工具把纸面上的格子搬出来，应该没有太多悬念。

这次我用 pdfplumber 处理一份自造中文报价单。目标很简单：把物料和金额提成一张能继续核对的表。不过，“眼睛看到一张表”和“程序读到一张表”，真的是一回事吗？

—第3步：先生成两份练习 PDF—

用纯文本编辑器新建生成练习PDF.py，以 UTF-8 保存到这个文件夹，完整内容如下。字体写进文本 PDF；随后把页面渲染成一张图片，再封装成另一份 PDF。后者没有文字层，不涉及 OCR。遇到同名输入文件，脚本会停止，不覆盖它们。

from pathlib import Path
import subprocess
from reportlab.pdfgen import canvas
from reportlab.pdfbase import pdfmetrics
from reportlab.pdfbase.ttfonts import TTFont
from reportlab.lib.utils import ImageReader

font = Path('/usr/share/fonts/truetype/wqy/wqy-zenhei.ttc')
if not font.is_file():
    raise SystemExit('没有找到中文字体，请先安装 fonts-wqy-zenhei')
for name in ['报价示例.pdf', '报价页面.jpg', '扫描样例.pdf']:
    if Path(name).exists():
        raise SystemExit(f'{name} 已存在，请换一个空文件夹，不覆盖原件')
pdfmetrics.registerFont(TTFont('Chinese', str(font), subfontIndex=0))
rows = [
    ['物料编码', '物料', '数量', '单价(元)', '金额(元)'],
    ['0007', '轴承', '12', '18.50', '222.00'],
    ['0012', '密封圈', '30', '2.40', '72.00'],
    ['0100', '胶带', '5', '9.90', '49.50'],
    ['合计', '', '', '', '343.50'],
]
w, h = 595.276, 841.89
c = canvas.Canvas('报价示例.pdf', pagesize=(w, h), invariant=1)
c.setTitle('示例公司报价表'); c.setAuthor('示例公司')
c.setFont('Chinese', 20); c.drawString(45, 780, '示例公司报价表')
c.setFont('Chinese', 12); c.drawString(45, 750, '报价编号：BJ-2026-1122')
c.drawString(45, 728, '以下物料与金额为自造示例，不是真实客户材料。')
xs, top, rh = [45, 135, 270, 340, 440, 550], 690, 36
for y in [top-i*rh for i in range(6)]: c.line(xs[0], y, xs[-1], y)
for x in xs: c.line(x, top, x, top-5*rh)
for i, row in enumerate(rows):
    for j, value in enumerate(row): c.drawString(xs[j]+8, top-i*rh-23, value)
c.setFont('Chinese', 11)
c.drawString(45, 470, '核对重点：编码前导零、三条明细、数量乘单价、合计金额。')
c.save()
subprocess.run(['pdftoppm', '-f', '1', '-singlefile', '-jpeg', '-scale-to',
                '1600', '报价示例.pdf', '报价页面'], check=True)
c = canvas.Canvas('扫描样例.pdf', pagesize=(w, h), invariant=1)
c.setTitle('示例报价图片页'); c.setAuthor('示例公司')
c.drawImage(ImageReader('报价页面.jpg'), 0, 0, w, h); c.save()
print('已生成：报价示例.pdf、扫描样例.pdf')

—第4步：用这个脚本抽出表格—

再新建抽取表格.py，把下面全文放进纯文本编辑器，以 UTF-8 保存到同一文件夹，不要变成 .py.txt。脚本没有替你判断财务口径：它只处理单页，从页面取一张表，再把单元格字符串写成 CSV（逗号分隔的表格文本）。

import csv, sys
from pathlib import Path
import pdfplumber

source, target = map(Path, sys.argv[1:3])
with pdfplumber.open(source) as pdf:
    if len(pdf.pages) != 1:
        raise SystemExit("本示例脚本仅处理单页PDF，请先确认页数")
    page = pdf.pages[0]
    table = page.extract_table()
    print(f"pages=1 chars={len(page.chars)} images={len(page.images)}")
    if not table:
        print("未找到可抽取的表格；没有写入CSV。先检查是否为纯图片或版面不适用。", file=sys.stderr)
        raise SystemExit(2)
    with target.open("w", encoding="utf-8-sig", newline="") as f:
        csv.writer(f).writerows(table)
    print(f"rows_with_header={len(table)} columns={len(table[0])}")
    print(f"csv={target.name}")

关键在先判断有没有表，再打开目标 CSV。没有找到时直接停止，避免生成一份空文件让人误以为完成。写文件时使用utf-8-sig，也就是带字节顺序标记的 UTF-8，方便表格软件识别中文；数字外观和编码字符串原样写出，不替你改小数位。

仍在“报价抽表”文件夹，运行下面两行。第二行紧跟第一行，显示上一条命令的退出码；中间不要插入别的命令。

—第5步：打开 CSV，先保住编码的零—

用LibreOffice Calc打开报价抽取.csv。出现文本导入窗口，字符集选Unicode（UTF-8）。这次分隔符是自动检测；先看预览是否正确分成各列。若没有分开，再手动选逗号。点预览里的第一列，在列类型里选Text（文本），然后导入。

字符集为 UTF-8，第一列为 Text。预览里编码开头的零还在。

先不要保存覆盖 CSV。检查0007、0012、0100，再看物料与数量有没有串列。此次含表头和合计共 25 个单元格，已与源表逐格对照一致。你换自己的材料，也要按表头、明细、合计的顺序核，不能只看文件能打开。

完整表格实际打开后的样子。合计显示 343.5，是 Calc 的一般数值显示；CSV 原字符串仍是 343.50。

  • 数量乘单价：12×18.50=222.00；30×2.40=72.00；5×9.90=49.50。
  • 三条金额相加：222.00+72.00+49.50=343.50。
  • 编码按文本读入；合计行仍在，脚本没有把它当明细删掉。后续做统计时要自己区分。

显示少一个零，不等于源数据少了一位。Calc 也会把 18.50 显示为 18.5。这次 CSV 的金额字符串未被修改。想让表格界面固定两位小数，可以另设显示格式。

—换成看起来一样的一页，结果变了—

前面很容易让人形成一个判断：只要 PDF 里的表格足够清楚，就能这样提出来。但把同一页变成纯图片后，这个判断就不成立了。前面生成的扫描样例.pdf，就是将报价页渲染成图片后重新放进 PDF 制作的，不是现场扫描仪或手机拍摄的文件。

原样本的图片版 PDF。阅读器里依然能看清表格，但页面内没有文字层。

先确认目录里没有以前留下的同名扫描抽取.csv，再做这个边界测试。无表保护不会删除以前的文件。

同一终端里，调用扫描样例.pdf 后得到 chars=0、images=1 和 exit:2；随后 no_csv:0 确认没有生成目标文件。

结果近景：chars=0，images=1。

脚本在没有表格时主动停止，退出码为 2。

这个 2 是附带脚本设定的保护码，不是 pdfplumber 原生错误码。继续单独调用库的 extract_table()，本次返回的是None，也就是没有抽到表。

同一纯图片样例，原生调用实际返回 native_table: None。

官方也明确说明库本身不提供OCR（光学字符识别）。所以这不是“图片识别不够准”，而是这条流程没有做识别。遇到这种材料，就停在文件类型判断；不要把空结果补成一张像是成功的表。

【广告位2】

—我的经验教训：先分清材料，再相信表格—

我这次最容易忽略的，是把“看着规整”当作“内部可读”。同一页，阅读器都能显示，程序拿到的内容却不同。以后遇到报价 PDF，我会先复制几段文字试试，再用少量页面抽取；能选中文字只是线索，不是成功保证。先分清材料，才不至于反复改命令，却始终在用错误的处理方式。

第二件事是把抽取和核账分开。抽出来的 25 格都对，不代表工具理解了税率、币种或业务合计。本次我按原表重新算乘法和加法，才确认这一份结果可继续整理。换自己的单据，至少核一个带前导零的编码、一条数量乘单价，以及最终合计；发现串列或金额不符，就回到源表。

还有一个脚本边界：它只处理单页，默认取页面中最大的一张表。多页、多表、合并单元格和没有表格线的版面，本轮没有验证通用做法。官方提供其他表格策略，但那需要另配参数、另做核验。遇到这些情况，别直接把这一页的结果外推成“任意 PDF 都能用”。

—最后—

我愿意把它留在“文本型报价单先抽出、再逐格核”的位置。能抽出来，就少一次照着页面重录；抽不出来，先确认文字层和版面，不用被“看得清就一定能提取”的印象带着走。把原 PDF 和 CSV 一起留好，下一次换材料仍从小样开始。
